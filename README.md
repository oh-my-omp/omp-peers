# omp-peers

English | [简体中文](README.zh-CN.md)

- **Peer endpoint (one per omp process)**
  - Main-session registration — Does: registers each main session (not subagents) with the process's endpoint; session id, title, cwd and idle state are read live, so `/new` and resume need no re-registration. When: on `session_start` of a main session. Example: `node.add(localMain(pi, ctx, ...), warn)` in `index.ts`.
  - IPC endpoint — Does: opens one endpoint per process for the same OS user, shared by every profile; it is the only liveness signal (no heartbeat, registry or cache). When: opened with the first registered main session. Example: `/tmp/omp-<uid>/peers/<pid>.sock` on macOS/Linux (parent must be the user's, mode `0700`), `\\.\pipe\omp-<pid>-<hash>` on Windows.
  - Wire protocol — Does: each connection carries one JSON request line (`list`, `ask`, `irc`) and one JSON response line; failures use fixed codes. When: on every `peer://` read or write. Example: error codes `bad_request`, `unsupported_version`, `target_not_found`, `ask_busy`, `ask_unsupported`, `ask_failed`, `delivery_failed`, `budget_exceeded`.
  - Unregistration and close — Does: removes the main session and closes the endpoint when the last main session leaves; `kill -9` and RPC-mode signals skip it and leave a socket file that refuses connections. When: on `session_shutdown`. Example: `/quit`, double Ctrl+C or `kill -TERM` close it.
- **`peer://` internal URL scheme**
  - Registration & settings — Does: registers the `peer://` handler on `InternalUrlRouter` when the `enabled` plugin setting is true (read once at process startup). When: at extension initialization in `index.ts`. Example: `peer://<pid>` targets a process's sole main session (following `/new` and resume); `peer://<pid>/<sessionId>` picks one when a process hosts several.
  - Discovery (`read peer://`) — Does: surveys live omp processes running `omp-peers` and lists their main sessions (address, title, cwd, idle or busy, plus `(you)` / `(this omp process)` markers). When: when a main session or subagent reads `peer://`. Example: `- peer://<address> "<title>" — <cwd> — idle`.
  - Side questions (`write peer://<address>?ask`) — Does: asks another main session a `/btw`-style side question and returns its answer as the write result; waits up to 5 minutes, cancelling aborts the target's side turn, one question per target at a time (`ask_busy`), answers over 32 KiB are cut with `[answer cut at 32 KiB]`, and `target_not_found` lists online peers. When: when a main session or subagent calls `write` with `?ask` (tier `read`, scope `coordination`). Example: `write(path: "peer://12345?ask", content: "Which branch are you on?")` → `Answer from peer://12345:`.
  - Side turn on the target — Does: the target answers through the host's `runEphemeralTurn` with its own model, system prompt, conversation and any in-flight tool call preview, adding nothing to its conversation and running no tools. When: when an `ask` request reaches the target's endpoint. Example: prompt `Side question from another omp main session (peer://…, cwd …):`, purpose `omp-peers-ask`.
  - Messages (`write peer://<address>`) — Does: sends a message (up to 64 KiB of UTF-8) into another main session's conversation and returns once injected, with no read receipt or offline delivery; rate-limited to 20 wake messages per 10 minutes per source process (`budget_exceeded`). When: when a main session or subagent calls `write` on `peer://<address>` (tier `read`, scope `coordination`). Example: `write(path: "peer://12345", content: "PR #12 is merged")` → ``Delivered to peer://12345. It was idle and starts a turn on it now. A reply arrives as an incoming peer message and wakes you; do not `wait` for it.``.
  - `irc:incoming` injection — Does: injects the message as an `irc:incoming` custom message delivered as an aside: an idle target starts a turn, a busy one reads it at its next step without interrupting its tools. When: when an `irc` request reaches the target. Example: `<irc>` wrapper instructing the recipient to reply via `write` (`path: "peer://<address>"`, `content: "…"`).
  - One-way subagent senders — Does: marks questions and messages from subagents as one-way, because subagents have no `peer://` address; recipients answer through the side turn only and never message back. When: whenever the sender has `taskDepth > 0`. Example: `It is one-way: a subagent has no peer:// address, so nothing you write reaches it.`
